# 讲解深度与调用路径

用于新案例、重写主线或增讲一个关键机制。小范围纠错直接复用已有学习目标和深度选择。

## 先拆解，再确认学习重点

1. 先核查足以分清对象与边界的材料。按依赖拆出定位与动机、完整调用路径、关键决策、内部机制、效果与证据。每项写一个读者要回答的问题，并判断它是否是后续内容的前置。
2. 把知识点分到三层。优先沿用用户已明确的目标和熟悉项；只对会改变主线或下钻重点的未知项提问。

   | 深度 | 放什么 | 怎么讲 |
   | --- | --- | --- |
   | 简讲 | 已掌握的背景、为后续搭桥的概念 | 一句话交代本案例中的职责，给需要的定义 |
   | 细讲 | 学习目标、关键决策和看懂主线所需的交接 | 用一个可跟踪的例子，解释原因、输入、状态与输出；留一个可预测的变化 |
   | 按需展开 | 精确谓词、完整参数、内部实现、源码、实验条件 | 放在对应机制旁；当用户要排错或理解该机制时，提到细讲层 |
3. 需要校准时，先给一份带建议的知识地图，再问一两道具体问题。例如“入口、组件如何交接、结果怎样验证，这三段你已经熟悉哪些？哪一段想跟一个实际例子？” 用户已给侧重点就直接采用；尚无反馈时按建议记录假设，继续核对证据并起草主线。
4. 选图前记录简短提纲。写明「读者能做什么 → 知识点/前置 → 简讲、细讲或展开 → 同一个例子 → 可核查出处」。新案例可放进 Case 的教学计划，局部迭代写在受影响章节的设计记录。保留一句可复述的职责、设计动机与前后连接，供熟悉背景的读者快速通过。

## 自顶向下讲调用

1. **是什么、为什么。** 先定位对象处在哪一层，接什么输入、交付什么；用一个现有路径的具体限制说明为什么设计它。讲集成时把“为什么有这个组件”和“为什么要接进宿主”拆成两个问题，分别交代双方收益、成立条件与代价。
2. **先走一条完整路径。** 选一个正常且可追踪的输入，从入口跟到结果被消费。标清谁发起、谁选择、谁执行、交接的值或句柄、状态归属和结果如何回来。换图或切观察层时，保留同一个请求、张量、任务或查询结果作为锚点。
3. **再解释决策和边界。** 在实际做选择的位置先用直白的问题解释判断理由，随后贴出候选路径、优先级、精确条件和固定出处。沿同一输入改一个条件，演示分支改变、回退或停止；源码没有回退时如实说明实际行为。区分配置/注册阶段、每次运行的选择和具体执行，逐条标出箭头表达的是调用、数据、控制或等待。
4. **最后下钻与验证。** 按读者关注点展开调用接缝、线程分工、缓存、同步或脚本细节；在讲分工前交代它解决的问题与额外成本。对性能写明 baseline、输入、环境和指标，区分代码推导、上游报告和本地复测。证据入口贴在对应判断旁。

## 从输入内容过渡到符号

1. 提纲里先写出读者会看到的一小段输入说明。交代输入是什么、谁产生它、其中一个具体值代表什么，以及处理后交给谁。自造数值标为教学例子；生产者尚未查明时，记录已知的入口条件与待查项。
2. 分清数据内容、维度、索引和执行配置。先解释量的含义，再给代码名和本例取值。例如，一个教学例子有 4 份部分和，第 2 份某位置的值为 0.5；4 是份数，第 2 份是所选索引，0.5 是数据值，每个计算块处理 8 项则是执行配置。具体形状和布局跟随对应 Case 的来源。
3. 关键符号在正文、首图或控件首次需要时就地说明，用同一个例子的取值或范围连接后续路径。进入公式或寻址前，读者应能复述一个值代表什么。

## 画图前和退回后

- 画图前走读提纲。读者只读主线，应能解释对象的职责与动机，指出一个具体输入值的含义、复述它怎样得到结果，并预测一个条件变化后的下一步。
- 页面退回时记录读者卡住的原问题与位置，区分前置解释缺失、调用断链、细节深度不匹配、事实错误和图形表达问题。先修对应层，再复查原问题及相邻过渡；事实变化先更新 Case/source map。重复出现的失效模式写回相应 skill。
